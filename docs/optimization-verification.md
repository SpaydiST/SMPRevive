## Сравнение нагрузки

Это отдельные локальные замеры, без статистических повторений и подключённых игровых клиентов. Они показывают сокращение конкретной работы; их нельзя переводить в обещание такого же роста TPS или скорости всего плагина.

| Сценарий | 1.3.0 | Итоговая 1.3.1 |
| --- | --- | --- |
| 200 сохранений неизменившихся данных 2000 игроков | 4048.4 мс суммарно | 32.6 мс суммарно; повторных сериализаций 0 |
| 128 офлайн-квитанций одного владельца | 128 чтений, 38.8 мс | 1 групповое чтение, 1.384 мс; найдены все 128 |
| 100 запросов алтарей чанка из реестра 4096 алтарей | Общий обход, 189.1 мс | Индекс чанка, 0.921 мс; каждый раз выбраны нужные 32 алтаря |
| 10000 голов со сроком через час | Периодический выбор до 64 ещё не готовых записей | 0 посещений очереди за 500 ручных pulse-вызовов |
| 32 прямых запуска полёта | 32 полёта, 32 отдельные задачи анимации и 1 задача сервиса | 16 полётов по лимиту, 0 отдельных задач анимации и 1 общая задача сервиса |
| 64 онлайн-игрока, 8 с аллергией | 1 получение общего онлайн-списка, 200 вызовов Player-прокси | 8 обращений по UUID, 40 вызовов прокси; посещены только 8 игроков с аллергией |

У сохранений одинаковые входные данные: 2000 UUID, по три поля, файл `players.yml` размером 184952 байта. В обоих вариантах все 200 записей на диск пропущены. Отличие новой версии — отказ от повторной подготовки YAML; её счётчик сериализаций остался равен 1 после исходного сохранения.

Файлы офлайн-игроков содержали одинаковые 128 BYTE-квитанций и занимали около 1.3 КБ; UUID и сжатые размеры различаются. Внутри прогона 1.3.1 одиночные чтения того же файла заняли 63.2 мс, групповое — 1.384 мс. Групповой API отсутствует в 1.3.0.

Внутри прогона 1.3.1 полный обход алтарей занял 148.6 мс против 0.921 мс для индекса. У аллергии в обоих вариантах прочитаны ровно 8 инвентарей: сокращены обход и обращения к игрокам. Проба полётов проверяет выделение задач и лимит, а не одинаковое число одновременно доставленных предметов.

Время 500 pulse-вызовов не используется как сравнение скорости очереди: 1.3.0 вызывает сервис раз в 2 тика и очередь каждый пятый pulse, 1.3.1 — каждый тик и очередь каждый десятый pulse. Оба режима сохраняют обработку раз в полсекунды. В baseline нет нового счётчика `queue-visited`; его ноль в сыром логе означает отсутствие метрики.

Baseline с семью сценариями выполнен до добавления отдельной пробы сигналов мира. После её добавления итоговый candidate прошёл восемь сценариев. Обновлённый одинаковый исходник harness компилируется и упаковывается против обоих JAR; в baseline новые API отмечаются как недоступные. Повторный серверный запуск baseline после этого дополнения не выполнялся.

## Очередь и сигналы мира

Стенд напрямую проверил внутренние индексы сервиса с 1000 ожидающими записями и отложенными повторами. 1000 одинаковых сигналов оставили один ожидающий UUID мира. Один проход посетил 64 записи и сделал 64 готовыми; все 1000 записей и индексов ожидания сохранились, после выборки готовых остались 936 будущих повторов.

Вторая проба использовала два UUID мира по 500 записей. Каждый проход посетил 64 записи, второй мир получил 64 готовые записи ко второму проходу. Проверяются индексы и ротация, а не подключение реальных игроков в два разных мира.

Отдельно проверена DeadlineQueue: 12 старых ID идут раньше четырёх более поздних; 1000 переносов одного ID и 512 пар переноса/отмены завершились пустыми индексами. Это проверка структуры очереди. Исправление срока в `scheduleRecord()` дополнительно проверено чтением исходника.
